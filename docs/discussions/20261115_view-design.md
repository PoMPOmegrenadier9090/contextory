# 種別のページをViewの置き場所にし、TimelineをViewの一つにする

記録日: 2026-11-15

Phase 4のViewの設計を、Tanaの種別（Supertag）のページを参考に決めた。結論は次のとおりである。

- 種別のページは、Viewのタブを切り替えて、その種別のObjectを見るページにする。名前、色、Fieldなどの定義は、別の画面「種別の設定」へ移す。
- Viewは、名前、表示形式、条件、並べ替え、列を持ち、種別ごとに複数作れる。
- 表のViewでは、列の見出しからFieldを足したり変えたりできる。
- Objectのページの専用のTimelineは廃止し、Viewの表示形式の一つにする。
- ObjectのページのViewは、種別の設定で定義する（案A）。どのProjectを開いても、同じタブが並ぶ。
- 文書へのViewの埋め込みは後回しにする。

同じ日に実装した。実装した内容と、設計から変えた点は最後の節に書いた。

## いまの画面

- 種別のページは、上に種別の定義（名前、色、チェックボックス、継承元、Field）を並べ、下にその種別のObjectを作成日の新しい順に出している。Fieldの値は出ず、絞り込みも並べ替えもできない。
- Objectのページは、本文の下にTimelineを出している。Contextでつながる記録と`@`の言及を時系列に混ぜ、種別で絞り込める。

[設計案](../object-document-design-proposal.md)では、Viewからも文書と同じObjectを作れること、Projectのページでは全種別を混ぜた一覧を標準にせず用途別に並べること、既定のViewを継承できる形を検討することを決めていた。[Phase 3への引き継ぎ](20261112_phase3-handoff.md)では、Viewを既製のヘッドレスな部品と自前の問い合わせ層で作ることにしている。

## 種別のページ

```text
#Task                                    [＋ 作成] [⋯]
[すべての#Task] [未完了] [今週] [＋ Viewを追加]
───────────────────────────────────────────
Title            Status   期限    Context      ＋
...
```

- 見出しの右に「＋ 作成」と「⋯」を置く。「⋯」の「種別の設定」から、名前、色、チェックボックス、継承元、Fieldの定義を開く。今の種別のページにある設定の欄は、この画面へ移す。
- 見出しの下にViewのタブを並べる。種別を作ると、最初のView「すべての#◯◯」（表）を一つ作る。
- 「＋ Viewを追加」で、名前、表示形式、条件を決めてViewを足す。

## Viewが持つもの

| 項目     | 中身                                                             |
| -------- | ---------------------------------------------------------------- |
| 名前     | タブに出す名前                                                   |
| 表示形式 | 表、Timeline。リスト、Board、Calendarは後で足す                  |
| 条件     | 種別、Context（配下まで含めるか）、Fieldの値、完了済みを含めるか |
| 並べ替え | Field、作成日、更新日                                            |
| 列       | 表で出すFieldと、その順番と幅                                    |

ViewはSQLiteに保存し、条件による絞り込みはサーバー側の問い合わせ層で行う。WebとDesktopは、これまでどおり`ObjectClient`を通して使う。

## 表

- 列はTitleとFieldにする。
- 列の見出しから、並べ替え、列の非表示、Fieldの名前と種類の変更ができる。右端の「＋」でFieldを足すと、種別の定義に加わる。
- テキスト、日付、選択のセルは、表の中で直接編集する。参照とContextは、`@`と同じ候補から選ぶ。
- 本文はセルで編集しない。行を開くと、Objectのページへ移る。
- 表から行を足すとObjectができる。Viewの条件を初期値にする。Projectのページの表で足したTaskは、そのProjectがContextになる。

## Timeline

今のTimelineを、表示形式「Timeline」として残す。

- Projectのページでは、条件を「このObjectの配下」にすると、今と同じく、Contextでつながる記録と`@`の言及を時系列に並べる。
- 種別のページで使うと、その種別のObjectを作成順に並べる。
- 言及（Objectではない段落など）を混ぜられるのはTimelineだけで、表には出さない。

これで、Objectのページにある専用のTimelineの欄を外す。

## ObjectのページのViewは種別の設定で定義する（案A）

Projectのページの本文の下にも、Viewのタブを置く（「Timeline」「Task」「Decision」など）。このViewは、種別の設定で「#Projectのページに出すView」として定義する。条件は「このObjectの配下」のように、開いているObjectを基準にして書く。

- どのProjectを開いても、同じタブが並ぶ。Projectを作るたびに設定しなくてよい。
- 既定は「Timeline」の一つだけにする。今のTimelineと同じ内容になる。

Objectごとに自由にViewを足す形（案B）も考えた。Projectごとに表示を変えられるが、作るたびに設定が要る。今回は案Aだけにし、Objectごとの追加が必要になったら足す。

## 最初に作る範囲

- 種別のページと、別画面の種別の設定
- 表示形式は、表とTimelineの2つ
- 条件は、Context、完了、選択と日付のField
- Objectのページは、案AのViewのタブ。既定は「Timeline」の一つ

リスト（入れ子のSubtask）、Board、Calendar、文書へのViewの埋め込みは後回しにする。Dailyの「この日のMemo」も「その日に作ったMemo」というViewで表せるが、作ったばかりなので今回は触らず、Viewがそろってから載せ替えるかを決める。

## 「配下」の取り方

今の実装では、ProjectとTaskのつながりは置き場所（Placement）ではなくContextで持つ。

- Projectの文書の中で`#`からTaskを作ると、そのTaskのContextに、最初の値としてProjectが入る（`savePage`と`createObject`）。Memoの中で作った場合は、Memo自身ではなく、MemoのContextを引き継ぐ（`inheritedContexts`）。
- 作った後はContextと置き場所は別のものになる。ContextのFieldを書き換えれば、文書の中の位置は変わらずにつながる先だけが変わる。Dailyに置いたMemoのContextにProjectを入れれば、そのMemoはProjectにつながる。
- Taskの中でSubtaskを作ると、SubtaskのContextはTaskになり、Projectにはならない。
- 取り出すときは、Contextを逆向きに再帰でたどる（`REACH`）。Projectを指すObject、そのObjectを指すObject…と集める。今のTimelineはこの全部を出している。

「配下」には次の二つがある。

| 取り方       | Projectから見て含まれるもの                   |
| ------------ | --------------------------------------------- |
| 直接         | ContextがそのProjectのObject（Taskなど）      |
| 配下のすべて | 直接のものに加え、Subtask、Taskの中のMemoなど |

## 決めたこと（2026-11-15追記）

- 種別を消したら、その種別のViewも消す。
- 継承した種別は、継承元のViewを使えるようにする。どう見せるか（タブに混ぜるか、複製して使うか）は実装のときに決める。
- Viewの条件の「配下」は、Viewごとに「直接」か「配下のすべて」かを選べるようにする。既定は、表は直接、Timelineは配下のすべてにする。
- 表には「階層で表示」のオプションを付ける。直接の配下を行にし、その下に、さらに配下のObjectを入れ子で出す。入れ子に出すのも、Viewの種別の条件に合うものだけにする。たとえばProjectのページの「Task」の表で使うと、ProjectのTaskの下にそのSubtaskが並び、Taskの中のMemoは出ない。配下のすべてを平たく並べると種別の違うものまで混ざるので、それを避けるためである。

- 「階層で表示」は最初に作る範囲に入れる。

## 実装

- Viewは種別ごとにSQLiteの`views`に保存する（スキーマはv5）。種別を作ると、種別のページ用の表「すべて」と、Objectのページ用の「Timeline」を一つずつ持たせる。すでにある種別には、DBを開いたときに同じ二つを足す。
- 絞り込みと並べ替えは`ObjectStore.queryView`で行う。画面は`ObjectClient.queryView`にViewのID、開いているObject、画面側の今日の日付を渡す。これまでの`timeline`と`objectsOfType`は`ObjectClient`から外した。
- Viewの追加、変更、削除は、種別の更新（`updateType`の`views`）で保存する。表のセルは`patchObject`の`fields`で保存する。Contextも同じ経路で書き換えられ、循環になる相手は取り込まない。
- 種別のページは、見出し、「＋ 作成」、「種別の設定」、Viewのタブを並べる。名前、色、チェックボックス、継承元、Fieldの定義は「種別の設定」へ移した。
- Objectのページは、本文の下のTimelineの欄をViewのタブに置き換えた。タブの「Viewの設定」で変えた内容は、その種別のすべてのページに出る。種別の設定の画面に専用の欄は作らず、Objectのページで直接足す形にした。
- 表では、テキスト、日付、選択のセルをその場で編集できる。参照とContextは、`@`と同じ候補から足し、×で外す。完了のチェックも表から切り替えられる。列の見出しから、並べ替え、列を隠す、Fieldの名前と型の変更ができ、右端の「＋」で種別にFieldを足す。最後の行に入力してEnterを押すと、Objectができる。Objectのページでは開いているObjectがContextになり、選択の条件は初期値になる。
- 「階層で表示」では、条件に合う直接の配下を行にし、その下に、条件に合う配下を入れ子で出す。種別のページでは、同じ種別のObjectを指していないものを最上位にする。
- 条件は、種別（Objectのページだけ）、範囲、完了、選択のField（選択肢と一致）、日付のField（今日、今日から7日以内、今日より前）を選べる。
- 表から書き換えたObjectが開いている文書に置いてあると、文書の版が変わる。そのまま本文を書くと競合になるので、表から書き込んだ後は文書を読み直す。

設計から変えた点と、まだ無いもの：

- 継承元のViewは、タブに混ぜずに「継承元から複製…」で自分のViewにする。タブに混ぜると、継承元と自分の「すべて」が重なって並ぶためである。
- 列を出す順番はFieldの順番と同じで、Viewごとには変えられない。列の幅も変えられない。Viewが持つのは、隠す列だけである。
- 種別の名前を変えると、その種別のViewと、その種別で絞っているほかの種別のViewが付いてくる。
- 種別を消す操作はまだ無いので、Viewを消す処理も無い。
- 文字と参照が混ざった値は、表では読むだけにした。書き換えると参照が消えるためである。
- 条件から外れたObjectの配下は、「階層で表示」では出ない。完了したTaskを隠すと、その下の未完了のSubtaskも隠れる。
- これまでのTimelineにあった「すべて／Task／Memo／Decision／言及」の切り替えは無くした。種別で絞りたいときは、Viewを足す。
- 条件はサーバーのSQLではなく、取り出した後に見ている。件数が増えて遅くなったらSQLへ移す。

確かめたこと：

- ObjectStoreのテスト：既定のView、範囲（直接、配下のすべて）、種別、完了、選択と日付の条件、並べ替え、階層、種別の名前変更、表からのContextの書き換え。
- HTTP APIのテスト：種別のViewと、ObjectのページのTimelineの取得。
- ブラウザー：種別のページの表、セルの編集、Viewの追加と設定、Projectのページで#Taskに絞った階層の表、行の追加、列のメニュー、種別の設定。本文に置いたTaskを表から変えた後に本文を書いても、競合にならないこと。
- Electronのsmoke。

## 試用後の見直し（2026-11-15）

試用で出た指摘を受けて、表と設定の画面を作り直した。

- 設定は、表の上の「表示」「並べ替え」「絞り込み」「⋯」に分けた。どれも小さな窓で開き、外を押すかEscapeで閉じる。列の見出しのメニューも同じ窓にした。
  - 表示：表示形式、階層、出す列。
  - 並べ替え：順序と、作成日、更新日、Title、各Field。
  - 絞り込み：種別と範囲（Objectのページだけ）、完了、Fieldごとの条件。Fieldを押すと開き、「値あり」「値なし」と、値（選択は選択肢、日付は今日、今日から7日以内、今日より前）を複数選べる。
  - ⋯：Viewの名前と削除。
- ブラウザー標準の選択と日付の部品をやめた。選択のセルは、候補を入力で絞って選ぶ。候補に無い値を入力すると、その値が入り、Fieldの選択肢にも加わる。日付のセルは、直接入力するかカレンダーから選ぶ。参照とContextも、同じ候補の窓から足す。
- Titleを表で書き換えられるようにした。ページは、行にマウスを乗せると出る「↗」から開く。参照が混ざるTitleは、表では読むだけにしている。
- 階層で入れ子に出す種別を選べるようにした。これまでは、Viewが絞っている種別と同じ種別だけを入れ子にしていたので、TaskとSubtaskのように同じ種別が重なる場合にしか入れ子が出なかった。#Projectの表でTaskを入れ子に出す、Taskの下にMemoも出す、といった指定ができる。

入れ子の行の並べ替えと絞り込みは、次のとおりにした。段ごとの設定は作らない。

- 並べ替えは、入れ子の行にも同じものを使い、それぞれの親の下で並べる。作成日、更新日、Titleはどの種別でも効く。Fieldで並べている場合、そのFieldを持たない種別の行は、値が空のものとして扱う。
- 完了の条件は、入れ子の行にも掛ける。
- Fieldの条件は、Viewが絞っている種別の行にだけ掛ける。入れ子に出した別の種別には掛けない。Fieldが種別ごとに違うためである。

Tanaも、下の段については、値の有無と値での絞り込みまでにとどめている。段ごとに並べ替えや条件を持たせると設定が増えるので、必要になってから足す。

文書の中のFieldの行（選択と日付）も、表と同じ窓に替えた。値を押すと開き、選択は候補から選ぶか新しい値を入力し、日付は直接入力するかカレンダーから選ぶ。新しい値は、Fieldを定義している種別の選択肢に加わる。選択肢は、Objectを作ったときに写したものではなく、今の種別の定義から出す。窓の部品（`view-controls.tsx`）は、エディタからも使うので`packages/editor`へ移した。

残っているもの：種別の設定の画面と「Objectを作成」の窓は、まだブラウザー標準の部品のままである。

## 二度目の試用後の見直し（2026-11-15）

- 階層の行を畳めるようにした。配下のある行の左の「▾」で畳み、「▸」で開く。畳んだ状態は画面の中だけに持ち、保存しない。
- 並べ替えを複数のキーでできるようにした。「並べ替え」の窓で「＋ 並べ替えを足す」を押し、「まず」「次に」の順に、キーと昇順・降順を選ぶ。前のキーで値が同じ行を、次のキーで並べる。Viewには`thenBy`として保存し、一つ目は従来どおり`sort`と`desc`に置く。列の見出しから並べ替えると、そのFieldが一つ目になる。
- 「絞り込み」の種別と、「表示」の階層で選ぶ種別は別のものである。前者は行に出す種別（列もこの種別のFieldになる）、後者は行の下に入れ子で出す種別である。見出しを「行に出す種別」に変え、階層の欄に「行の下に出す種別」と書き添えた。
- Objectのページの表で、最後の行に「#Memo 考え」のように書くと、その種別で作れるようにした。種別の名前は大文字と小文字を区別しない。種別を絞っていないViewでも、この書き方なら追加できる。絞り込みの値を初期値にするのは、絞っている種別で作るときだけにした。別の種別で作ったObjectは、Viewの条件に合わなければ表には出ない。
- 追加の行で「#」に続けて打つと、名前の先頭が合う種別を入力欄の下に候補として出す。↑↓で選び、EnterかTabを押すか、クリックして「#Memo 」のように入れる。空白を打つと候補は消える。

DBのスキーマをv5に上げたので、古い版のアプリやサーバーでは開けなくなる。サーバーと画面は同じ版にそろえて更新する。
