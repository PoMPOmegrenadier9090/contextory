# 種別のページをViewの置き場所にし、TimelineをViewの一つにする

記録日: 2026-11-15

Phase 4のViewの設計を、Tanaの種別（Supertag）のページを参考に決めた。結論は次のとおりである。

- 種別のページは、Viewのタブを切り替えて、その種別のObjectを見るページにする。名前、色、Fieldなどの定義は、別の画面「種別の設定」へ移す。
- Viewは、名前、表示形式、条件、並べ替え、列を持ち、種別ごとに複数作れる。
- 表のViewでは、列の見出しからFieldを足したり変えたりできる。
- Objectのページの専用のTimelineは廃止し、Viewの表示形式の一つにする。
- ObjectのページのViewは、種別の設定で定義する（案A）。どのProjectを開いても、同じタブが並ぶ。
- 文書へのViewの埋め込みは後回しにする。

実装はまだ始めていない。

## いまの画面

- 種別のページは、上に種別の定義（名前、色、チェックボックス、継承元、Field）を並べ、下にその種別のObjectを作成日の新しい順に出している。Fieldの値は出ず、絞り込みも並べ替えもできない。
- Objectのページは、本文の下にTimelineを出している。Contextでつながる記録と`@`の言及を時系列に混ぜ、種別で絞り込める。

[設計案](../object-document-design-proposal.md)では、Viewからも文書と同じObjectを作れること、Projectのページでは全種別を混ぜた一覧を標準にせず用途別に並べること、既定のViewを継承できる形を検討することを決めていた。[Phase 3への引き継ぎ](20261112_phase3-handoff.md)では、Viewを既製のヘッドレスな部品と自前の問い合わせ層で作ることにしている。

## 種別のページ

```text
#Task                                    [＋ 作成] [⋯]
[すべての#Task] [未完了] [今週] [＋ Viewを追加]
───────────────────────────────────────────
Title            Status   期限    Context      ＋
...
```

- 見出しの右に「＋ 作成」と「⋯」を置く。「⋯」の「種別の設定」から、名前、色、チェックボックス、継承元、Fieldの定義を開く。今の種別のページにある設定の欄は、この画面へ移す。
- 見出しの下にViewのタブを並べる。種別を作ると、最初のView「すべての#◯◯」（表）を一つ作る。
- 「＋ Viewを追加」で、名前、表示形式、条件を決めてViewを足す。

## Viewが持つもの

| 項目     | 中身                                                             |
| -------- | ---------------------------------------------------------------- |
| 名前     | タブに出す名前                                                   |
| 表示形式 | 表、Timeline。リスト、Board、Calendarは後で足す                  |
| 条件     | 種別、Context（配下まで含めるか）、Fieldの値、完了済みを含めるか |
| 並べ替え | Field、作成日、更新日                                            |
| 列       | 表で出すFieldと、その順番と幅                                    |

ViewはSQLiteに保存し、条件による絞り込みはサーバー側の問い合わせ層で行う。WebとDesktopは、これまでどおり`ObjectClient`を通して使う。

## 表

- 列はTitleとFieldにする。
- 列の見出しから、並べ替え、列の非表示、Fieldの名前と種類の変更ができる。右端の「＋」でFieldを足すと、種別の定義に加わる。
- テキスト、日付、選択のセルは、表の中で直接編集する。参照とContextは、`@`と同じ候補から選ぶ。
- 本文はセルで編集しない。行を開くと、Objectのページへ移る。
- 表から行を足すとObjectができる。Viewの条件を初期値にする。Projectのページの表で足したTaskは、そのProjectがContextになる。

## Timeline

今のTimelineを、表示形式「Timeline」として残す。

- Projectのページでは、条件を「このObjectの配下」にすると、今と同じく、Contextでつながる記録と`@`の言及を時系列に並べる。
- 種別のページで使うと、その種別のObjectを作成順に並べる。
- 言及（Objectではない段落など）を混ぜられるのはTimelineだけで、表には出さない。

これで、Objectのページにある専用のTimelineの欄を外す。

## ObjectのページのViewは種別の設定で定義する（案A）

Projectのページの本文の下にも、Viewのタブを置く（「Timeline」「Task」「Decision」など）。このViewは、種別の設定で「#Projectのページに出すView」として定義する。条件は「このObjectの配下」のように、開いているObjectを基準にして書く。

- どのProjectを開いても、同じタブが並ぶ。Projectを作るたびに設定しなくてよい。
- 既定は「Timeline」の一つだけにする。今のTimelineと同じ内容になる。

Objectごとに自由にViewを足す形（案B）も考えた。Projectごとに表示を変えられるが、作るたびに設定が要る。今回は案Aだけにし、Objectごとの追加が必要になったら足す。

## 最初に作る範囲

- 種別のページと、別画面の種別の設定
- 表示形式は、表とTimelineの2つ
- 条件は、Context、完了、選択と日付のField
- Objectのページは、案AのViewのタブ。既定は「Timeline」の一つ

リスト（入れ子のSubtask）、Board、Calendar、文書へのViewの埋め込みは後回しにする。Dailyの「この日のMemo」も「その日に作ったMemo」というViewで表せるが、作ったばかりなので今回は触らず、Viewがそろってから載せ替えるかを決める。

## 「配下」の取り方

今の実装では、ProjectとTaskのつながりは置き場所（Placement）ではなくContextで持つ。

- Projectの文書の中で`#`からTaskを作ると、そのTaskのContextに、最初の値としてProjectが入る（`savePage`と`createObject`）。Memoの中で作った場合は、Memo自身ではなく、MemoのContextを引き継ぐ（`inheritedContexts`）。
- 作った後はContextと置き場所は別のものになる。ContextのFieldを書き換えれば、文書の中の位置は変わらずにつながる先だけが変わる。Dailyに置いたMemoのContextにProjectを入れれば、そのMemoはProjectにつながる。
- Taskの中でSubtaskを作ると、SubtaskのContextはTaskになり、Projectにはならない。
- 取り出すときは、Contextを逆向きに再帰でたどる（`REACH`）。Projectを指すObject、そのObjectを指すObject…と集める。今のTimelineはこの全部を出している。

「配下」には次の二つがある。

| 取り方       | Projectから見て含まれるもの                   |
| ------------ | --------------------------------------------- |
| 直接         | ContextがそのProjectのObject（Taskなど）      |
| 配下のすべて | 直接のものに加え、Subtask、Taskの中のMemoなど |

## 決めたこと（2026-11-15追記）

- 種別を消したら、その種別のViewも消す。
- 継承した種別は、継承元のViewを使えるようにする。どう見せるか（タブに混ぜるか、複製して使うか）は実装のときに決める。
- Viewの条件の「配下」は、Viewごとに「直接」か「配下のすべて」かを選べるようにする。既定は、表は直接、Timelineは配下のすべてにする。
- 表には「階層で表示」のオプションを付ける。直接の配下を行にし、その下に、さらに配下のObjectを入れ子で出す。入れ子に出すのも、Viewの種別の条件に合うものだけにする。たとえばProjectのページの「Task」の表で使うと、ProjectのTaskの下にそのSubtaskが並び、Taskの中のMemoは出ない。配下のすべてを平たく並べると種別の違うものまで混ざるので、それを避けるためである。

## 決まっていないこと

- 「階層で表示」を最初に作る範囲に入れるか。
- Viewの条件を組み立てる画面の形。最初に扱う条件は上の範囲に絞る。
- 種別の名前を変えたときに、保存したViewをどう扱うか。
