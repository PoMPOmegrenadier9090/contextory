# リリース前の変更計画：Objectを自動で消さず、ゴミ箱・種別の削除・バックアップを足す

記録日: 2026-11-16

初回リリースまでに、データを失わず、間違えて作ったものを片付けられるようにする。そのために、文書から外したObjectを自動で消す処理をやめ、消すのはゴミ箱を通した明示的な操作だけにする。あわせて、種別の削除、バックアップ、Markdownでの書き出しを足す。

このメモで決めたいのは、末尾の「未決の論点」にある5点である。実装はこの計画の確認後に始める。

## 決まったこと

- 置き場所の無いObject（どの文書にも置かれていないObject）を認める。文書から外しても、自動では消さない。Viewの定義と同じく、DBに置いたままにする。
- 消す操作は「ゴミ箱へ移す」と「ゴミ箱から完全に削除」だけにする。
- 初回リリースでは、オフラインでの編集を扱わない。扱うときは、端末間の競合をどう解くかを先に設計する。
- 次の4つは、リリースに必要である。Objectの削除とゴミ箱、Daily→Projectのような移動を安全にすること、バックアップと書き出し、種別の削除。

対象外：検索の画面、日付・選択のFieldのキーボード操作、モバイル実機での確認など、日々の使い勝手の項目はこの計画に含めない。リリースまでに別に進める。

## 1. 文書から外したObjectを消さない

今の`savePage`は、保存の最後に、その文書から外れてほかのどこにも置かれていないObjectを`deleteObject`で消している。これが次の3つの問題の元になっている。

- 取り消しで戻しても、作成日時と手で付けたContextが失われる。
- Dailyで切り取ってProjectへ貼ると、貼る前にDailyの保存が走った場合にMemoが消える。
- 表や「Objectを作成」の窓で作ったObjectは、もともとどこにも置かれていない。文書側の削除と、置き場所の無いObjectの扱いが食い違っている。

変更は、`savePage`の末尾の削除をやめるだけである。外れたObjectは`placements`から外れ、行は残る。

- 取り消しや貼り付けで同じidのObjectが文書に戻ると、`upsertObject`は既存の行を更新する。作成日時もContextも残る。
- 移動（切り取って貼る）は、保存の順番によらず安全になる。
- 文書で行を消したTaskは、種別のページや表に残り続ける。片付けたいときは、ゴミ箱へ移す（2.）。

確かめること：同じObjectを「コピー」して別の文書に貼ると、同じidが二つの文書に置かれる。今の作りで二か所に置けるのか、貼るときに新しいidを振るべきかは、実装の前にエディタで確かめる。

## 2. ゴミ箱

### 持ち方

`objects`に`deleted_at`（NULLなら生きている）を足し、スキーマをv6に上げる。ゴミ箱へ移しても、行、Field、Context、言及の索引は消さない。戻したときに元どおりになるようにするためである。

ゴミ箱のObjectは、次のすべてから外す。

- `@`の候補と検索（`search`）
- Viewの行（`queryView`）、Timeline（`timeline`）、Dailyの一覧（`overview`）
- ほかのObjectのContextの継承と、推移的に集めるContext

参照チップやContextのチップは、相手がゴミ箱にあれば、取り消し線の付いた「削除済み」の見た目にする（エディタにある`data-type="missing"`と同じ見た目）。

### 操作

| 操作             | 場所                   | 内容                                                                 |
| ---------------- | ---------------------- | -------------------------------------------------------------------- |
| ゴミ箱へ移す     | Objectのページ、表の行 | 文書に置かれていれば、その文書から外す（後述）。`deleted_at`を入れる |
| 戻す             | ゴミ箱の画面           | `deleted_at`を空にする。置き場所の無いObjectとして戻る               |
| 完全に削除       | ゴミ箱の画面           | 確認の後、今の`deleteObject`で消す。元に戻せない                     |
| ゴミ箱を空にする | ゴミ箱の画面           | 確認の後、ゴミ箱のすべてを完全に削除する                             |

ゴミ箱の画面は、ナビゲーションの下に「ゴミ箱」として置き、移した日時の新しい順に並べる。期限が来たら自動で消す仕組みは作らない。自動で消さないという方針に合わせる。

### 文書に置かれているObjectを移すとき

文書に置かれたままゴミ箱へ移すと、文書の中に消えたはずのObjectが残る。移すときは、置かれている文書の本文からそのObjectのブロックを取り除き、同じtransactionで索引も作り直す。確認の窓で「2件の文書から外れます」のように件数を出す。

本文を書き換えると、その文書の版が変わる。開いている画面は競合として扱われ、読み直すか上書きするかを選ぶ。上書きを選ぶと、ゴミ箱のObjectが文書に戻る。`savePage`は、ゴミ箱にあるidを文書の中に見つけたら、ゴミ箱から戻す。文書に置いたことを、戻す操作とみなす。

ゴミ箱へ移したObjectの本文に置かれていたObjectは、そのまま生きている。表や種別のページには出る。親を戻すと、親の本文の中に元どおり置かれている。

## 3. 移動を安全にする

1.で削除をやめれば、切り取りと貼り付けの順番によってMemoが消えることは無くなる。別の作業は要らない。テストに「Dailyから外して保存し、その後でProjectに同じidで置くと、作成日時とContextが残る」を足す。

## 4. 種別の削除

ユーザーが作った種別だけを消せるようにする。最初から入っている種別（Task、Memoなど）は消せない。種別の設定画面に「種別を削除」を置く。

消せないのは次の場合で、理由と件数を出す。

- その種別のObjectが残っている（ゴミ箱の分も数える）。先にゴミ箱へ移し、完全に削除する。
- ほかの種別がこの種別を継承している。

消すときは、同じtransactionで次も消す。

- その種別のField定義と、その種別のView
- ほかの種別のViewで、この種別を絞り込みや階層に使っている指定（名前を変えたときに書き換えている箇所と同じ）

Objectの種別を変える操作は、今は無い（`ObjectPatch`に種別が無い）。そのため、種別を消すには、その種別のObjectをすべて消す必要がある。Objectを残したまま別の種別へ移す操作は、この計画には含めない。

## 5. バックアップと書き出し

二つを分けて作る。

|        | バックアップ                   | Markdownの書き出し                   |
| ------ | ------------------------------ | ------------------------------------ |
| 目的   | 失ったときに元へ戻す           | アプリの外で読む、ほかのツールへ移す |
| 形式   | SQLiteのファイルをそのまま複製 | 文書とObjectごとの`.md`              |
| 情報   | すべて残る                     | Field、Context、Viewの一部は落ちる   |
| 戻し方 | ファイルを置き換える           | 戻せない（読み込みは作らない）       |

### バックアップ

`better-sqlite3`の`backup()`で、書き込み中でも整った複製を作る。

- サーバー：起動時と1日1回、データフォルダの`backups/`に日付つきの複製を作り、新しい7個を残す。`GET /api/next/backup`で、その場の複製を落とせるようにする。
- Desktop：メニューに「バックアップを書き出す…」を足す。手元のDBなら`backup()`、サーバーにつないでいればAPIから落とし、保存先を選んで書く。
- 戻し方は、まず手順を`docs/server-setup.md`に書く。アプリの中から戻す操作は、初回リリースでは作らない。

古い版のファイルを新しい版のアプリで開くと、起動時にスキーマが上がる。新しい版のファイルは、古い版のアプリでは開けない。

### Markdownの書き出し

`packages/core`に、DBの内容からファイルの一覧（パスと本文）を作る関数を置く。保存とzipは呼ぶ側で行う。

- Dailyは`daily/2026-11-16.md`、Objectは`objects/<種別>/<Title>-<id>.md`にする。
- 先頭にYAMLでid、種別、作成日時、完了、Field、Contextを書く。
- 本文の中のObjectは、チェックボックス付きの箇条書きとそのファイルへのリンクにする。参照もリンクにする。
- Desktopはフォルダを選んで書く。Webはサーバーでzipにして落とす。zipを作るには依存パッケージが一つ増える。

## スキーマとAPI

スキーマはv6に上げ、`objects.deleted_at`を足す。サーバーとアプリは同じ版にそろえて更新する。

| 追加するAPI                                     | 内容                                   |
| ----------------------------------------------- | -------------------------------------- |
| `POST /api/next/objects/:id/trash`              | ゴミ箱へ移す                           |
| `POST /api/next/objects/:id/restore`            | ゴミ箱から戻す                         |
| `DELETE /api/next/objects/:id`                  | 完全に削除する（ゴミ箱にあるものだけ） |
| `GET /api/next/trash`、`DELETE /api/next/trash` | ゴミ箱の一覧、空にする                 |
| `DELETE /api/next/types/:name`                  | 種別を消す                             |
| `GET /api/next/backup`                          | DBの複製                               |
| `GET /api/next/export/markdown`                 | Markdownのzip                          |

`ObjectClient`（`core`）、Desktopの手元のクライアントとIPC、HTTPのクライアントに、同じ操作を足す。

## 進め方

次の順で、それぞれ別のcommitにする。1.と3.は小さく、ほかの作業の前提になるので先に入れる。

1. 自動削除をやめる（1.と3.）
2. ゴミ箱（v6、API、画面）
3. 種別の削除
4. バックアップ
5. Markdownの書き出し

検証は、それぞれ`corepack pnpm check`、`corepack pnpm build`、テスト用のサーバー（5196）での画面の確認、Electronのsmokeで行う。`ObjectStore`のテストには、移動、ゴミ箱へ移して戻す、置かれたObjectを移したときの文書の変化、種別を消せない場合を足す。

## 実装の結果（2026-11-16）

計画の5項目を、ブランチ`codex/release-data-safety`（PR #1のブランチから切った）で実装した。計画と違うところと、未決の論点の扱いは次のとおり。

- 1.と3.は一つのcommitにした。2.〜5.は`ObjectStore`の同じ箇所を触るため、一つのcommitにまとめた。
- ゴミ箱へ移す確認の窓は、ブラウザーの`confirm`を使う。置かれている文書の件数は出さず、「置かれている文書の本文からも外れる」とだけ書く。
- Markdownの書き出しを作る関数は、`core`ではなく`storage-node`に置いた。DBの行とFieldを読むためである。zipは依存を増やさず、Nodeの`zlib`で作る。
- 論点2（置き場所なしの絞り込み）は作っていない。
- 論点3（コピーして貼ったObject）：エディタは貼り付けで新しいidを振らない。同じidが二つの文書に置かれ、どちらで書いても同じObjectが変わる。自動削除をやめたので、片方の文書から消してもObjectは残る。
- 論点4は、計画どおり1日1回・7個とした。
- 論点5は、初回リリースに含めた。

## 未決の論点

1. **作業するブランチ。** PR #1（View）はmergeされていない。この作業はスキーマv5の上に作るので、PR #1をmergeしてからmainで進めるか、PR #1のブランチから新しいブランチを切るかを決めたい。
2. **文書で行を消したObjectの扱い。** 1.の方針では、文書でTaskの行を消しても、Taskは表に残る。消したつもりのTaskが残るのを片付けやすくするため、表に「置き場所なし」で絞る条件を足すか。
3. **コピーして貼ったObject。** 同じidのまま二つの文書に置くか、貼るときに新しいidを振るか（1.で確かめてから決める）。
4. **バックアップを残す数と間隔。** 計画では1日1回、7個としている。
5. **Markdownの書き出しを初回リリースに含めるか。** バックアップがあれば、データを失うことは防げる。書き出しは、アプリの外で読むためのものである。
