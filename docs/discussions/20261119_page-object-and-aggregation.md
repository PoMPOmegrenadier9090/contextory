# 自由に書けるページと、Viewで範囲を決める集約の検討

記録日: 2026-11-19（2026-11-20に追記）

状態: UX調査と設計議論の整理。所属を1つにする変更とInboxは実装した。その後、Contextを活動に限る方針と、Objectの住所を種別のDBにする方針に合意したが、これらはまだ実装していない。

当初は、ユーザーから「Object間の関係は自由に作り、推移的集約ではたどる経路を明示する」という案が出ていた。Object Typeで探索経路の既定を作り、Object単位でも調整する構想である。Codexは、用途別の集約テンプレートとViewごとの例外に分ける案を提案した。

その後の議論で、Area・Project・Taskを固定の活動として扱い、Person・Paperなどの具象と分ける方向に合意した。集約は活動の階層を軸にし、どの具象を取得するかを選べるようにする。詳細は「[活動と具象を分け、活動の階層を軸に集約する](#活動と具象を分け活動の階層を軸に集約する)」に記す。

さらに、所属と本文上の配置を独立させ、配置の変更で所属が自動では変わらないようにする方針に合意した。Objectの原本を1か所に決める案と、画面の初案は「[所属と本文上の配置を分ける](#所属と本文上の配置を分ける)」以降に記す。

実装後の議論では、Contextは常に活動を指し、具象はContextを持たないことにした。具象で書くときのContextは、書いた場所ではなく、そのときの活動の状態で決める。あわせて、Objectの住所を種別のDBとし、本文の埋め込みをすべて窓として扱う形に改めた。それより前の節にある原本の案と、具象の所属の規則は、この見直しで置き換えた。詳細は「[実装後の見直し：Contextを活動に限り、Objectの住所を種別のDBにする](#実装後の見直しcontextを活動に限りobjectの住所を種別のdbにする)」に記す。

この文書は、最初の入力・操作UXの調査から、この集約案に至るまでをまとめる。現在の実装、ユーザーの要望、Codex・Claudeの提案、未決事項を区別する。コードやデータ形式は変更していない。

## 書く場所を作る負担と、元の作業へ戻りにくいこと

最初の問題意識は、入力や操作の体験をNotion並み、少なくともSiYuanのように信頼して使える状態へ近づけたい、というものだった。ユーザーが特に引っかかると答えたのは「ページを探す・開く・戻るとき」である。

その後、操作の前段にも負担があると分かった。Daily以外で自由に書く場所を増やすには、種別付きのObjectを作る必要がある。「まだAreaやProjectとは言えないが、なんとなくまとめたい」ときに、先に分類や構成を決めることになる。

Quick CaptureでMemoを残し、Contextへつなぐ方法は合理的だが、文章や候補を並べ替えながら一つのまとまりを作る用途には、それだけでは足りない。ユーザーが求めているのは、白紙ページを増やし、その場でTaskやView、必要ならDBを足し、別のページへ後から移せる小回りである。一方で、多機能化によって本来の使い方がぶれることも避けたい。

実装調査で見つかった主な点は次のとおり。画面操作による再現を伴わない所見も含む。

| 対象                   | 実装から確認した状態・懸念                                                                       | 議論した改善候補                                           |
| ---------------------- | ------------------------------------------------------------------------------------------------ | ---------------------------------------------------------- |
| ページの往復           | 開くたびにエディタを作り直し、先頭へスクロールする。訪問履歴や編集位置の復元はない               | 戻る・進む、カーソルとスクロール位置の復元                 |
| 探し直し               | ⌘K検索はあるが、空欄では最近開いたページが出ず、開くたびに検索語を消す                           | 閲覧履歴、検索語と選択結果の保持                           |
| 本文への到達           | 全文検索の抜粋やTimelineの言及から、ページIDだけで開く                                           | 該当ブロックへの移動と強調表示                             |
| 寄り道と入力の継続     | 参照先を読むプレビューがない。Viewの変更やCapture追加でも本文のエディタを作り直す経路がある      | 開く操作の統一、プレビュー、再読込時の編集状態の保持       |
| 下書きと変更の取り消し | CaptureはEscで下書きを破棄する。種別変更では一部のField値が消え、戻しても復元されない            | 下書き保持、影響の説明、復元手段                           |
| コピー                 | Objectをコピーして貼っても同じIDを使い、同じ記録を共有する                                       | 共有して配置する操作と、独立した複製の区別                 |
| 保存状態               | 本文の保存待ち中も「保存済み」が残り得る。保存競合後のページ移動では未保存内容を失うおそれがある | 状態表示の修正、移動しても未保存内容を保持する仕組み       |
| メニュー               | 検索と他のダイアログで、キー操作やフォーカス管理がそろっていない                                 | 開く・選ぶ・閉じる・元の入力へ戻る操作の統一               |

| 見た目                 | 文字記号とSVGのアイコンが混在する。主要操作とキャンセルの見た目が同じ。本文のH1〜H3が同じサイズ  | 操作の意味が分かる強弱、アイコン・文字階層・明暗配色の統一 |

保存競合後の移動による内容の消失と、ダークモード時の候補表示の不整合は、コードからの推定を含む。実画面での再現確認が必要である。外観全体が「チープ」であるかは、実画面を取得できず判断していない。

## ページとObjectを同じ記録単位として扱う案

ユーザーは、ページとObjectはメモをまとめる単位として等価だと考えている。ページを自由に入れ子・埋め込みにでき、必要になったときにデフォルトのプロパティや集約の設定を与え、Objectとして使うイメージである。

Codexは、ページを基本の記録単位にし、Task・Projectなどの種別や共通プロパティ、既定の表示を後から付ける案として整理した。役割を変えてもIDと本文を保つ。普通の文章はそのまま残し、必要な部分だけを独立した記録として切り出す。

この案では、表示単位を次のように統一できる。

| 表示する場所           | 同じ記録の見せ方                          |
| ---------------------- | ----------------------------------------- |
| 単独のページ           | 本文、プロパティ、子ページ、Viewを開く    |
| 他のページへの埋め込み | 本文や畳んだ見出しを表示する              |
| DBの行                 | Titleとプロパティを並べ、開くと本文を読む |

書き始める際にAreaやProjectと決める必要をなくし、「考え中」のようなページをそのまま残せるようにする。種別を付ける利点は、繰り返し使うプロパティや表示の設定をまとめて用意できることに置く案である。普通のページも集約の起点にできるようにすることは、Codexから提案した。

ただし、ページとObjectの保存形式や、種別なしのページをどう表すかは未決定である。現在の保存層では、Objectに属さない文書として認めているのはDailyだけである。白紙ページの作成に加えて、以下の集約や設定範囲も検討する必要がある。

## NotionのようなDBとObject＋Viewの両立

ユーザーは、白紙からその場でViewや独立したDBを作れる柔軟さを求める一方、機能を増やしすぎることを懸念している。Codexは当初、白紙ページ、個別View、独立DB、後から移す操作を改善候補として挙げたが、独立DBを最初から一式作るのは範囲が大きいと見直した。

検討した整理は、記録の本体をObjectに統一し、一覧の行も本文から切り出した記録も同じIDで扱う、というものである。候補一覧の行をTaskにしたら、同じ記録が全体のTask一覧にも現れる。DBのために別のTaskをコピーしない。

その場合も、情報ごとの共有範囲を決める必要がある。

| 情報                           | 議論した共有範囲の案           |
| ------------------------------ | ------------------------------ |
| 本文・Title・Taskの共通Field   | 同じObjectを表示する場所で共有 |
| 並べ替え・絞り込み・表示する列 | そのViewだけ                   |
| 比較用の評価など一覧専用の項目 | その一覧だけ                   |

最後の一覧専用項目は、現在の種別がFieldを持つ仕組みの拡張を要する。ページ固有のViewを足すだけでは、独立した列の定義まで実現できない。単純な表で足りる用途と、行ごとの本文や独自項目・絞り込みが必要な用途を分け、独立DBの範囲を決める案が出た。採用範囲は未決定である。

## 複数の親を持つContextとMemoの混在

ユーザーが想定する入れ子は、重なり合う枠を持つグラフである。同じページが複数の親を持ち、Contextを汎用的な入れ子関係として使う。親から下層の種別や深さを指定して、推移的に集約したい。

この構造では、PersonやResourceを複数の活動で共有すると、関係のないMemoまで混ざる場合がある。例として、次の関係を考えた。

```text
Project B.Context = [Area B]
Person.Context = [Area A, Project B]
Memo B.Context = [Person]
```

集約の向きでは、どちらの経路も成立する。

```text
Area A → Person → Memo B
Area B → Project B → Person → Memo B
```

Contextをすべて推移的にたどるなら、Memo Bは両方のAreaへ届く。このデータには、Memo Bがどちらの活動の記録かという情報がない。出力する種別や最大深さだけで、同じMemo型・同じ位置にある記録の活動を判別することはできない。

現行の`timeline()`は、Contextの配下だけでなく、その配下のObjectへの言及も拾う。一時DBでは、Memo BのContextをProject BにしてPersonへ言及した場合も、Person経由でArea AのTimelineに出ることを確認した。所属と参照を分けるだけでは、集約側の現在の規則によって混在が残る。

ここまでに出た案と、その扱いは次のとおり。

| 案                                              | 制御するもの                                         | 議論での扱い                                                                                                   |
| ----------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 所属と参照を分ける                              | MemoはProjectへ所属し、Personとは参照でつなぐ        | Codexが提案。MemoをPersonの子のまま扱う構想から前提を変えていた                                                |
| 文脈付きContext                                 | 親IDと、その関係が有効な文脈・配置を組にして保存する | Codexが提案。ユーザーは、Context given ContextはUXを煩雑にするため好ましくないと指摘した                       |
| Area・Project・Taskなどだけを固定で特別扱いする | 決まった型の組合せだけを推移させる                   | ユーザーは選択肢として言及したが、用途が増えると破綻する可能性を懸念した。後に、活動と具象を分ける形で合意した |
| Viewで探索経路を定義する                        | 実データの関係は自由にし、集約する経路を選ぶ         | ユーザー提案。後に、活動と具象を分ける案へ進んだ                                                               |

文脈付きContextでは、例えば`{ parent: Person, within: Project B }`のように関係を保存する案を確認した。Project B自体が複数Areaに属するなら、さらに配置IDや経路が必要になる。この入力・管理の複雑さを避けたいというユーザーの意向を受け、次に、集約定義側へ制御を移す案を検討した。

初期の説明では、Memoの所属を変える案と探索を止める案が混在した。Contextが単純な紐づけのままなら、Personという型だけを暗黙に特別扱いして解決したことにはできない。どの経路を採用するかを、明示的な規則として持つ必要がある。

## 関係を自由に作り、Viewで集約する範囲を決める案

ユーザーは、GraphQLのように、どこまでたどるかをクエリ側で定義する発想を提案した。UI上でObject Type間の接続を選び、つながっている経路だけを集約する。Objectごとの設定を毎回行う負担を避けるため、Type単位の基底グラフを用意し、Object粒度でも設定できる形を考えている。

Codexは、型の接続を用途別の集約テンプレートとして持ち、必要な例外をViewごとに設定する案を提案した。これは実データに許す関係を決めるスキーマではなく、そのViewが取得する経路の設定である。以下は、用途に応じて編集できるテンプレートの例である。

| 親→子の種別        | 集約での扱いの例                  |
| ------------------ | --------------------------------- |
| Area→Project       | 先へ進む                          |
| Project→Task       | 先へ進む                          |
| Task→Task          | 同じ規則で繰り返し進む            |
| Project・Task→Memo | Memoを取得して止める              |
| Project→Company    | 就活用ViewではCompanyまで取得する |
| Project→Paper      | 研究用ViewではPaperまで取得する   |

CompanyやPaperの先も集めたい場合は、そのViewで経路を追加する。集約に含めない関係も、実データのContextとしては作れる。GraphQLは経路を明示する発想の参考として挙げた。Task→Taskの繰り返しなどは、Contextory側の集約規則として検討する。

表示対象と探索経路は分ける。例えばMemoだけを表示するViewでも、途中にあるProjectやTaskを通過できるようにする。必要になる扱いは、「取得して止める」「取得して先もたどる」「結果には出さず通過する」である。深さの指定とこれらの規則の組合せは未決定である。

ユーザーが挙げた「就活ではCompany、研究ではPaperを集約したい」という違いを、全Projectに共通の型階層へ押し込む必要はない。同じProject型でも、置いたViewが違う集約テンプレートを使える案である。

Object粒度の調整について、Codexは「このViewでは、このPersonの先へ進まない」のような例外を提案した。Object本体へ設定すると別のViewにも影響するため、例外はそのViewに持たせる。設定の保存先と共有範囲は、まだ決めていない。

現行の[View定義](../../packages/core/src/object-model.ts)には、種別、直接の配下／配下のすべて、階層表示、入れ子に出す種別がある。ただし、親の型と子の型の組合せによる経路定義や、表示と通過の分離は実装していない。Viewは種別が所有しており、用途別・ページ固有の設定をどう保存するかも設計変更の対象になる。

## クエリ定義を、メモを書く前の必須作業にしない

ユーザーは、入力側の複雑さを避けても、今度はクエリ定義がボトルネックになるのではないかと懸念している。新しいページや活動のたびに型グラフを描く必要があれば、アプリを自分に合わせて整備する負担が残る。

負担を減らす案として、Codexは次を挙げた。

- 白紙ページを作るときには集約設定を要求しない。
- 集約が欲しくなったら、既定の用途別テンプレートを使う。
- 結果から「この型の下も集める」「このObjectで止める」を変更できるようにする。
- 取得した経路と、探索を止めた場所を確認できるようにする。
- 種別なしのページを挟んだ場合も、下層のTaskなどへたどれる既定を検討する。

型グラフのUIは全体の確認・調整に使い、すべての利用者の最初の入口にはしない案である。Codexは、まず「用途別テンプレート＋このViewでの変更」の二段階を提案した。型・活動・Object・Viewへ多段に自動継承する仕様は、この議論では決めていない。

ただし、型ルールとObject単位の例外で解ける範囲にも限界がある。同じCompanyの下に就活AのMemoと就活BのMemoがあり、両方ともMemo型なら、`Company→Memo`を有効にすると両方が入る。Company単位で停止しても、両方が止まるだけである。

活動別に分けたい場合に考えた方法は、次の二つである。

- Company経由では拾わず、その活動からTaskなどを経由して到達するMemoを拾う。
- Memoが、その活動にもContextで紐づいていることを取得条件にする。

活動との関係が入力データにない場合は、クエリ側でも自動判別できない。逆に、その関係が既存のContextのリンクとして残っていれば、文脈付きContextを追加せず、経路や取得条件として扱える。これを入力時の操作とどうつなぐかは未決定である。

この時点では、型を使って設定の手間を減らし、活動の境界を型だけですべて表そうとはしない構成を検討していた。この後の議論で、次の節の方向へ進んだ。

## 活動と具象を分け、活動の階層を軸に集約する

### 閲覧経路からContextを補う案は退けた

Claudeは、混在の原因を二つに分けた。どの辺をたどるかという経路の問題と、Memo BがどちらのProjectの記録かがデータにないという情報の問題である。後者はクエリ側では解決できないため、Project B → Person と移動してから書いたMemoに、Project BもContextとして自動で付ける案を出した。

ユーザーは、この案ではContextを制御しにくいと指摘した。スマホでは、Quick Captureに直接書くか、検索でページを開いてから書くことが多い。どちらも閲覧経路を持たないので、この案は前提から合わない。

### ユーザーの案は、活動の階層を固定し、具象は選んで取得すること

ユーザーは、活動とPerson・Resource・Paper・Bookのような具象を分けて考えるべきではないかと提案した。活動の階層を固定して集約の中心にし、どの具象を取得するかはオプションで選ぶ。すべてを正しく紐づけるのは難しいので、残る不足はAIの組み込みで補う考えである。

Claudeは、両者の違いを次のように整理した。これまでの混在は、性質の違う2種類のObjectを同じContextでつなぎ、具象を通る経路まで推移的にたどっていたことから起きていた。

|              | 活動（Area・Project・Task） | 具象（Person・Paper・Book・Companyなど） |
| ------------ | --------------------------- | ---------------------------------------- |
| 構造         | 階層があり、集約の軸になる  | 多くの活動から参照される                 |
| 時間         | 始まりと終わり、状態を持つ  | 時間に区切られず、残り続ける             |
| 集約での扱い | 推移的にたどる              | 選んだ種別を1段だけ取得し、先へ進まない  |

以前ユーザーは、決まった型だけを特別扱いすると、用途が増えたときに破綻するおそれを挙げていた。固定するのを「活動か具象か」という役割にとどめ、ユーザーが作る種別を具象とすれば、種別を足しても集約の規則は変わらない。現実の同じ対象が両方の性質を持つ場合は、二つに分ける。例えば、具象のCompanyとしてA社を置き、Projectとして作った「A社の選考」から参照する。

### 合意した方向

| 論点           | 方向                                                                                                                                            |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| 活動の種別     | Area・Project・Taskに固定する。ユーザーが自由に作る種別は具象とする                                                                             |
| 入れ子         | Areaは最上位に置き、入れ子にしない。ProjectはArea・Projectの下、TaskはProject・Taskの下に置ける。Taskは、後の議論で具象の下にも置けることにした |
| 親の数         | 所属する親は1つだけにする                                                                                                                       |
| 種別なしページ | 配下は通過させる。活動として扱うかについて、ユーザーは判断を保留した                                                                            |
| AIによる紐づけ | 推定した紐づけは、ユーザーが承認してから反映する                                                                                                |

種別なしページについて、Claudeは、活動とは別に「親の所属を引き継ぐ入れ物」とする案を出した。Project Bの下の種別なしページに置いたTaskは、集約ではProject Bの配下として扱う。Paperの下に置いた読書メモのページは、Paperの一部になる。最上位に置いたページはどの活動にも属さず、後からProjectに変えてもIDと本文を保つ。

### 所属は1つ、参照は複数とする

親を1つにすると、Objectのつながりは2種類に分かれる。Claudeは、Memoも含めて次の形にする案を示した。

- 所属：1つだけ。集約は所属を推移的にたどる。
- 参照：複数持てる。具象へのリンクや@言及がこれに当たり、集約ではたどらない。

当初の「重なり合う枠を持つグラフ」という構想は、所属の木と参照の組み合わせで表すことになる。現行のObjectは`contexts`に複数のContextを持ち、@言及も別に索引している。そのため、この形にするには保存形式の変更が要る。

### 集約は、活動の木をたどり、選んだ具象を添える

Claudeが整理した活動ページでの集約は次のとおりである。

1. 活動の所属を推移的にたどる。種別なしページは通過する。
2. たどった活動に所属するMemoを集める。
3. オプションで取得する具象の種別を選び、たどった活動から1段だけ取得する。就活ならCompany、研究ならPaperを選ぶ。

就活・研究のような用途の違いは、新しい活動の種別ではなく、Projectの用途テンプレートで表す案をClaudeが出した。テンプレートには、よく使うプロパティと、取得する具象の種別を持たせる。前の節で検討した用途別の集約テンプレートは、ここに置くことになる。

具象のページでは向きを逆にし、その具象を参照するMemoを活動ごとに分けて並べる。具象に所属したまま活動が決まっていないMemoは、「活動未定」として並べる。

### スマホからの入力では、活動を後から決める

Quick Captureで書いたMemoや、検索で開いたPersonのページで書いたMemoは、活動が決まっていなくても保存できるようにする。後者は、まずPersonに所属する。AIが活動を推定して提案し、ユーザーが承認すると、所属はProject Bへ移り、Personは参照として残る。

承認制にするため、Claudeは、提案を通常のリンクとは別に保存し、承認したときに所属・参照へ変える案を出した。リンクごとに「ユーザーが付けたか、AIが推定したか」を記録する必要はなくなる。

冒頭の共有Personの例に当てはめると、次のようになる。

| Memo Bの状態                    | Area A | Area B | Personのページ      |
| ------------------------------- | ------ | ------ | ------------------- |
| Personに所属（承認前）          | 出ない | 出ない | 「活動未定」に出る  |
| Project Bに所属し、Personを参照 | 出ない | 出る   | Project Bの欄に出る |

## 所属と本文上の配置を分ける

### 具象は活動の木に所属させない

Claudeは当初「具象は常に最上位に置き、活動からは参照する」と書いた。ユーザーは、活動から参照することには同意したが、「最上位」という点に引っかかった。

Claudeが意図していたのは、具象を活動の下に所属させないことである。例えばA社を就活Projectの子にすると、別の就活や研究からA社を使うときに、所属が就活に固定される。A社の下のMemoも就活の集約へ流れ込み、最初に議論した混在が戻る。

具象の下に別のObjectを置くことまで禁じる必要はない。Book › Chapter、Company › 部署のような具象の入れ子は許してよい、とClaudeは整理した。具象の親になれるのは、具象か種別なしページだけとする案である。

### 活動もObjectのまま扱い、具象の下にTaskを置ける

ユーザーは、活動の種別を固定したことで、活動がObjectではなくなったように見えると指摘した。Claudeは、固定するのは種別の定義だけで、Area・Project・TaskもObjectとして本文やプロパティを持つと説明した。

```text
Object
├ 活動：Area・Project・Task（固定。集約の軸になる木を作る）
├ 具象：Person・Company・Paper・Book…（ユーザーが作る種別）
├ Memo：記録
└ 種別なしページ：親の所属を引き継ぐ入れ物
```

ユーザーは、具象の中にTaskを置けるのは悪くないと考えている。「田中さんにお礼を送る」「この本の3章を読む」のように、どの活動にも属さない作業がある。Claudeもこれに賛成した。集約の規則では、次のように扱われる。

| 見る場所             | 田中さんの下のTask                       |
| -------------------- | ---------------------------------------- |
| 田中さんのページ     | 出る                                     |
| 全体のTask一覧       | 出る                                     |
| 就活などの活動の集約 | 出ない。活動の木は具象の中へ進まないため |

あるTaskを就活として扱いたくなったら、所属を就活に移し、田中さんは参照として残す。移した後も、田中さんのページには「就活」の欄に出る。

これに合わせて、Claudeは、Inboxに出すのを所属がまったくないものだけにする案を出した。具象の下に置いたものは利用者が意図して置いたものなので、未整理として扱わない。AIの提案は、具象のページの中で控えめに示す程度にとどめる。

### 配置が変わっても所属は自動で変えない

具象のページの本文に書いたTaskの所属を就活へ移したとき、本文の中のTaskをどうするかが論点になった。ユーザーは、活動の中で親を付け替えるときにも同じ問題が起きると指摘した。そのうえで、Objectの配置を自動で変えるのは入力体験として良くないので、所属と配置は独立させるべきだと判断した。配置されている場所を親にはしない。

| 見え方                     | 決めるもの                         | 変わるとき                       |
| -------------------------- | ---------------------------------- | -------------------------------- |
| 本文（配置）               | どこに書いたか、どこに埋め込んだか | ユーザーが本文を編集したときだけ |
| パンくず・集約の欄（所属） | どこに属するか                     | ユーザーが所属を変えたときだけ   |

Dailyに書いたMemoで今起きていることを、すべてのObjectに広げる形である。次の規則で合意した。

- 作成時は、書いた場所を所属の初期値にする。Dailyで書いたものは所属なしにする。
- 所属を変えても、本文の中の位置はそのまま残す。
- 本文の中でページ間を移しても、所属は自動では変えない。ただし「所属もProject Bにする」のようなボタン付きの通知は出す。
- 本文に置かれていなくても、所属があれば親ページの集約やパンくずからたどれる。

所属が埋め込み先のページと違うときは、ブロックの端に小さく所属を表示する案をClaudeが出した。

```text
田中さんのページ（本文）
  □ お礼のメールを送る
  □ 面接の日程を返信する          › 就活
```

### Objectの原本を1か所に決める

ユーザーは、`@`参照とObjectの実在の関係が分かりにくくなっていると指摘した。埋め込むこと自体よりも、ObjectがType一覧の中にあるのか本文の中にあるのかが一貫していないことが問題だという。Notionでは、新しく作ったページが関係のないDBに現れることはない。この構想では、Object Typeの一員でありつつ本文に配置されたページでもあり、それが綺麗でない。この点から自動では消さないほうがよいとも考えたが、誤って作ったTaskなどを整理する手間が生まれるので、入力体験として直感的ではないとも感じている。

Claudeは、Objectが現れる場所が4種類あり、そのどれが本体か決まっていないことが原因だと整理した。

| 現れる場所       | 現行の扱い                           |
| ---------------- | ------------------------------------ |
| 本文中のブロック | 配置。同じObjectを複数の場所に置ける |
| `@`のチップ      | 言及（参照）                         |
| Type一覧・集約   | 検索の結果                           |
| 単独のページ     | Object自身を開いたもの               |

現行のゴミ箱の判定は「最後の配置を外したらゴミ箱へ」という数え方である（[保存層](../../packages/storage-node/src/object-store.ts)の本文保存処理）。その削除が最後の配置かどうかは画面から分からないため、同じBackspaceでも消えるときと消えないときがある。

そこでClaudeは、LogseqやTanaのブロック参照に近い次の決め方を提案した。

- 原本：Objectを作った場所。本文中の1か所か、本文に置かない単独の存在のどちらかで、必ず1つだけ。
- 窓（埋め込み）：原本を他の本文に表示したもの。左端の線などで、見た目から原本と区別できるようにする。
- `@`参照：意味のつながり。消してもリンクが外れるだけ。
- Type一覧・集約：条件に合うObjectの索引で、置き場所ではない。NotionのDBが入れ物であるのに対し、「その種別を付けたもの」の一覧になる。

原本の場所は所属とは関係しない。所属は意味の上での親、原本は本文がどこに書かれているかを表す。削除については、ユーザーは「Objectを直接消したらObject自体を消す」とした。Claudeの案では、削除の操作ごとに次のように扱う。

| 操作                           | 結果                                                             |
| ------------------------------ | ---------------------------------------------------------------- |
| 原本をBackspaceなどで消す      | Objectをゴミ箱へ移す。他に窓があれば、件数と元に戻すボタンを示す |
| 窓を消す                       | その場所から外れるだけ                                           |
| `@`を消す                      | 参照が外れるだけ                                                 |
| 一覧や集約で消す               | 明示的な「ゴミ箱へ」の操作として、Objectを消す                   |
| 原本を切り取って別の場所へ貼る | 原本が移る。所属は変えず、所属も変えるかの通知を出す             |
| 原本をコピーして貼る           | 窓を作るか、独立した複製を作るかを選ぶ                           |

誤って作ったTaskは、書いた場所でBackspaceを押せば消える。窓を消してもObjectは残る。最後の行は、UX調査の表にあった「コピー」の課題に対応する。

### Viewから作ったObjectは単独の原本になる

ユーザーは、Viewから登録したObjectをどう扱うのか、すべてを本文に書かせる想定なのかを尋ねた。Claudeは、Viewからの作成も受け付け続け、単独の原本として扱うと答えた。

現行の[View](../../packages/ui/src/views.tsx)の追加行は`createObject`を呼び、本文に置かないObjectを作る。Contextの初期値はViewを置いたページで、絞り込みで選択肢が一つに決まるFieldは、その値を初期値にする。新しいモデルでは「所属はViewのページ、原本は単独」と読み替えられ、作り方を変える必要はない。

本文で書いたTaskとの違いは原本の場所だけで、Type一覧や集約には同じように出る。Claudeは、本文で書いたTaskにだけ、Viewの行から「書いた場所へ移動」する操作を付ける案を出した。

ただし、現行の削除判定とは食い違う。Viewで作ったTaskを本文へ埋め込み、その埋め込みを消すと、配置がなくなったとみなされてゴミ箱へ移る。新しいモデルではこれは窓を消す操作なので、Taskは残るべきである。実装するときは、判定を「最後の配置かどうか」から「原本かどうか」に変え、原本の場所を保存する必要がある。

## 画面の初案

この配置モデルを前提に、Claudeが画面の初案を出した。採用は決まっていない。

| 画面             | 初案                                                                                                                   |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------- |
| サイドバー       | Daily、Inbox、Area › Projectの木、最上位の種別なしページ、具象の種別ごとの一覧、ゴミ箱。Taskは木に出さない             |
| スマホの下部バー | Daily・Inbox・検索・＋（Capture）                                                                                      |
| ページ上部       | 所属を表すパンくず。親が1つなのでパンくずは1本に決まる。最後の区切りから所属を変える。具象のページでは種別名を出す     |
| Quick Capture    | 所属は「未定」のまま保存できる。最近使った活動を候補に出し、AIを組み込んだ後はAIの候補も並べる。`@`で参照を作る        |
| 活動ページ       | 本文の下に、Task・Memo・選んだ具象の集約の欄を縦に並べる。表示する具象は用途テンプレートが初期値を決め、Viewに保存する |
| 具象ページ       | その具象に関係するMemoやTaskを活動ごとに分けて並べる。活動に属さないものは別の欄に出す                                 |
| Inbox            | 所属のないものの一覧。スマホでは右スワイプで候補を承認し、左スワイプで所属を選ぶ。まとめて承認もできる                 |
| 種別の付け外し   | 種別なしページに「種別を付ける」を置く。最上位にあるときだけAreaも選べる。IDと本文は保つ                               |
| 作成             | 本文中の`/ページ`や`/Task`で子として作り、`@`では参照だけを作る                                                        |

InboxとDailyの関係について、ユーザーは「Inboxに入れて後で振り分け、Dailyからは引き続き並べて読める」形かを確認した。Claudeは、Inboxは置き場所ではなく所属が決まっていないものを集めたViewであり、振り分けてもDailyには書いた日の記録として残ると答えた。ユーザーはInboxの案をとても良いと評価した。

## 実装後の見直し：Contextを活動に限り、Objectの住所を種別のDBにする

2026-11-20に、ここまでの合意の一部を実装し、それを踏まえて議論を続けた。その結果、前の節までの案のうち、次のものを置き換えた。

| 前の案                                   | 置き換えた案                                                             |
| ---------------------------------------- | ------------------------------------------------------------------------ |
| 具象は活動の木に所属させない             | 具象はContextを持たない。Contextは常に活動を指す                         |
| 作成時は、書いた場所を所属の初期値にする | 具象のページでは、そのときの活動の状態で決める                           |
| 閲覧の経路からContextを補う案は退ける    | 具象のページに限り、活動から移ってきた状態をContextに使う                |
| Objectの原本を本文中の1か所に決める      | Objectの住所は種別のDB。本文の埋め込みはすべて窓で、書いた場所を記録する |
| 言及の集約は未決定                       | 活動への言及は推移的に集約し、具象への言及は直接の言及先にだけ出す       |

### 実装したこと

この議論の前に、2つのPRを作ってmainへmergeした。インストール済みのアプリはまだ置き換えていない。

- [#4](https://github.com/PoMPOmegrenadier9090/contextory/pull/4)：Contextに置ける親を1つにした。親になれなかったContextは、全種別に足した「参照」の行へ移す。既存のDBは、開いたときにスキーマv8へ移行する。親子にできる種別の組は`canContain`で決め、具象は具象の下にだけ置ける規則にした。
- [#5](https://github.com/PoMPOmegrenadier9090/contextory/pull/5)：所属のないProject・Task・Memo・Decisionを集めるInboxを足した。Areaと具象は出さない。各行から、親になれるものだけを候補にして所属を選べる。

v8の移行は、#4の時点の規則で書いてある。このままアプリを置き換えると、Areaなどの下にある独自種別のObjectが親から外れる。この節で決めた規則に直してから置き換える必要がある。

### Contextは常に活動にする

ユーザーは、まず所属規則を「Area→Project→Taskの順番を守れば大丈夫」とした。Area直下のTaskも許すことになる。Taskをサイドバーの木に出す必要もないとした。

具象の扱いは、議論の中で二度変わった。最初は、すべてのObjectが具象の親になれてよいとした。次に、推移的に集約したいのは活動だという認識から、具象の親は活動だけとした。最後に、具象はContextを持たなくてよいと考えた。

> 研究というcontextでmemoを論文につけたとき、別にそのcontextは論文のcontextから引き継がれたものではなく、アプリ内の状態から導かれたものだと思います。（ユーザー）

Claudeもこれに賛成した。具象にContextを持たせても、集約には使われず、「具象のContextを初期値にするか」のような判断が増えるだけだからである。

| 種別                           | Context                               | 具象との関係             |
| ------------------------------ | ------------------------------------- | ------------------------ |
| Area                           | なし                                  | —                        |
| Project                        | AreaかProject                         | 企業などのFieldで持つ    |
| Task                           | Area・Project・Task                   | Fieldか、参照の行で持つ  |
| Memo・Decision・種別なしページ | 活動か、外側から引き継ぐ。空ならInbox | 参照の行で持つ           |
| 具象                           | 持たない                              | 自分が具象として存在する |

具象との関係は、Contextとは別のプロパティで持つ。ユーザーが挙げた例では、「リクルートの面接」というTaskのContextは就活で、企業のFieldにリクルートが入る。リクルートのページからは、このFieldによって参照される。Memoのように専用のFieldを持たないものは、#4で足した参照の行を使う。

### Contextは、どこで書いたかより、どの状態で書いたかで決める

ユーザーは、Contextは書いた場所よりも、書いたときの状態で決まるほうが大事だと考えるようになった。活動の中で書いたものや、活動に紐づけたものは確定的に決まる。具象で書く場合は、そのときの活動の状態を使う。

| 書いた場所               | Context                 | 参照の行                           |
| ------------------------ | ----------------------- | ---------------------------------- |
| 活動のページ             | その活動                | なし                               |
| Memo・種別なしページの中 | 外側のContextを引き継ぐ | なし                               |
| 具象のページ             | 活動の状態。無ければ空  | その具象を自動で入れる             |
| Daily・Quick Capture     | 活動の状態。無ければ空  | 具象のページから開いたら、その具象 |

Contextが空のものはInboxに入り、後から振り分ける。参照の行に具象を入れるのは、Quick Captureで書いたMemoが具象の本文に残らないためと、自動で入った値が違っていても行から外せるためである。

状態を取り違えると、Memoが黙って別の活動へ入る。そこで、Claudeは次の規則を出し、ユーザーが合意した。

- 引き継ぐ：活動のページから、本文やViewのリンクで具象へ移ったとき。そこから戻るときも引き継ぐ。
- 外す：検索、サイドバーの具象の一覧、Daily、Inboxから開いたとき。
- 自分で決める：パンくずの区切りから切り替える。具象のページでは、パンくずの活動を外すボタンも置く（ユーザーの要望）。

スマホでは検索から開くことが多く、状態は外れやすい。具象で書いたMemoの多くはInboxに入ることになり、Inboxでの振り分けとAIの候補で受け止める。

Quick Captureについて、ユーザーは、保存後に「本文に追加しますか？」と聞かれる仕組みが欲しいかもしれないとした。Quick CaptureのMemoは今日のDailyの末尾に置かれる。Claudeは、確認の画面ではなく、「リクルートの本文にも追加」というボタン付きの通知にする案を出した。

具象のページには、その具象を参照の行・Field・`@`で直接指しているものを、Contextの活動ごとに分けて並べる。「[画面の初案](#画面の初案)」の具象ページと同じ形である。

既存データの移行は、次の案である。具象自身のContextは参照の行へ移す。具象をContextにしていたObjectは、具象を参照の行へ移し、Contextを空にする。どちらも関係は参照の行に残るので、失われない。

### 言及は、活動へのものだけ推移的に集約する

ユーザーは、言及とContextは別物と考えて、直接の言及先にだけ出すとした。Claudeは、`@`で始まる段落を、相手をContextにしたMemoに変える案を出した。ユーザーはこれを退けた。集約する対象が2つに分かれるのは変な感じがするうえ、ページの文章が細切れになるからである。

その後Claudeは、Dailyに普通の段落として書いたことがどの活動にも届かない点を、目的の妨げとして挙げた。ユーザーは、活動なら推移的に集約してよいのではないかと問い、Claudeも賛成した。言及の集約で漏れが起きたのは、具象が集約の経路に入っていたからである。Contextを活動に限った後なら、活動への言及を祖先まで集めても漏れない。

| 言及先                      | 出るところ                     |
| --------------------------- | ------------------------------ |
| 活動（Area・Project・Task） | その活動と、祖先の活動のページ |
| 具象                        | その具象のページだけ           |

規則は「活動の集約は、その活動の木に属するものと、その木への言及からなる」の1つで言える。今のコードも言及を経路付きで祖先へ集めているので、変えるのは具象を経路から外すところである。画面では、属しているものと言及しているだけのものを見分けられるようにする。

### Objectの住所は種別のDBにする

ユーザーは、DBとViewを分けて考えていなかったと述べ、これが混ざっていることが、Objectの所在が曖昧になる原因かを尋ねた。ユーザー自身は、Viewは集約のためのものとだけ考えていた。

Claudeは、原因の大きな部分はそこにあると答えた。NotionではDBがページの住所で、Viewは1つのDBの見え方である。今のContextoryでは、種別のページがDBのように見える。種別が列とViewを持ち、表から行を足すとObjectが作られる。一方で同じObjectが本文にも置かれるので、住所が2つあるように見える。

Claudeは、原本は本文中の1か所という案のまま、Viewを窓として整理した。これに対してユーザーは、Viewから新しくObjectを作れるようにしたいので、本文を所在とするのは違う可能性があると述べた。ObjectはObject typeのDBに入り、Viewや本文の埋め込みはそれを参照するだけ、という形である。Claudeは原本の案を取り下げ、これに賛成した。

| 言葉            | 意味                                                 | 変わるとき                     |
| --------------- | ---------------------------------------------------- | ------------------------------ |
| 所在            | 種別のDB。すべてのObjectが1行ずつある                | 種別を変えたとき               |
| 窓（埋め込み）  | 本文やViewにObjectを表示したもの。いくつあってもよい | 本文を編集したとき             |
| 書いた場所      | 作ったときの本文。ViewやDBから作ったものはなし       | 切り取って別の場所へ貼ったとき |
| 所属（Context） | 集約に使う活動                                       | ユーザーが変えたとき           |
| 参照            | 何についての記録か。具象など                         | ユーザーが変えたとき           |

今の配置は、窓の一覧として残す。書いた場所は新しく保存する値である。Objectのページには、書いた場所へのリンクと、ほかの窓の一覧を出す。

独立DB（一覧専用の列を持つ表）については、Claudeは新しい概念として増やさない案を出した。読みたい本の一覧なら、#Bookのような種別を作り、Fieldを列にして、その種別を集めるViewをページに置けば表せる。

### 削除は、書いた場所での操作だけをゴミ箱へ送る

窓を消してもObjectが残るだけだと、本文で誤って作ったTaskがDBに溜まる。Claudeは、書いた場所だけを特別に扱う案を出した。

| 操作                                  | 結果                                                         |
| ------------------------------------- | ------------------------------------------------------------ |
| 書いた場所でBackspace・Delete・上書き | ゴミ箱へ移し、「元に戻す」付きの通知を出す                   |
| ほかの窓を消す                        | その場所から外れるだけ。「この場所から外しました」と通知する |
| 表やページのメニューから削除          | ゴミ箱へ移す                                                 |
| 最後の窓を消す                        | Objectは残る。DBと、所属がなければInboxに出る                |

削除の意図はエディタで判定し、明示的に「ゴミ箱へ」を送る。保存の時点で「最後の配置が消えたか」を数える今の判定はやめる。何が起きたかは通知で分かるので、原本と窓を見た目で区別しなくて済む。

切り取りとドラッグについては、ユーザーが、貼らなかったことをどう識別するのかと指摘した。切り取った内容はクリップボードにあるだけなので、識別はできない。書いた場所から切り取るたびにゴミ箱へ送ると、Objectが失われる。ユーザーは、ゴミ箱へは送らず削除候補として見せるのが妥協点ではないかとした。Claudeは賛成し、次の仕組みを出した。

1. 書いた場所の窓が切り取りやドラッグで消えたら、「置き場所をなくした」という印を付ける。
2. 貼った先の保存で印の付いたObjectが入ってきたら、そこを新しい書いた場所にして印を外す。
3. 印が残ったものは削除候補として見せる。

同じページの中での切り取り・貼り付けや並べ替えは、1回の保存で済むので印は付かない。削除候補を出す場所として、Claudeは、Inboxに「置き場所をなくしたもの」の欄を設け、「ゴミ箱へ」と「このまま残す」を置く案を出した。Viewから作ったObjectは、もともと書いた場所がないので候補に入らない。

### 既存のObjectを本文に埋め込めるようにする

既存のObjectを本文に埋め込めるようにしたい、というのがユーザーの要望である。置き場所をなくしたObjectを、もう一度本文に出すためにも要る。今のブロックメニューには「新しいObjectを埋め込む」しかない。

データ層は、同じObjectを複数のページに埋め込むことにすでに対応している。ページの版は埋め込んだObjectの内容まで含めて計算するので、別のページで編集した後に古い内容のページを保存しようとすると、衝突として断られる。Claudeは、作るときの注意として次を挙げた。

- 先にObjectの内容（タイトル・本文・Field）を読み込み、それを入れたブロックを挿入する。IDだけの空のブロックを保存すると、Objectの内容が空で上書きされる。
- 自分自身や、自分の配下の本文には埋め込めないようにする。
- 埋め込んでもContextは変えない。ページ間の移動と同じく、Contextを変えるかの通知は出してよい。
- 書いた場所は変えない。ただし「置き場所をなくした」印のあるObjectなら、そこを新しい書いた場所にする。

| 入口                              | 操作                                                       |
| --------------------------------- | ---------------------------------------------------------- |
| ブロックメニューと`/`             | 「既存のObjectを埋め込む」から検索して選ぶ                 |
| `@`の候補                         | 参照を作るほか、別のキーで埋め込みも選べるようにする       |
| Inboxの「置き場所をなくしたもの」 | 「元の場所に戻す」で、最後の書いた場所の末尾へ埋め込み直す |

### 種別なしページ

種別なしページについて、ユーザーは、最上位に作るか、Objectの本文の中で`/page`で作るものと考えていた。親の所属を引き継ぐ。Claudeは、今のMemoの振る舞いにほぼ重なるとして、組み込みの種別`page`として持つ案を出した。

- 本文で`/page`で作ると、置いた場所の活動が所属になる。最上位に作ったものは所属なしになる。
- 中で作ったObjectは、ページではなく、ページの所属を引き継ぐ。ページは所属先にならない。
- 最上位のページはサイドバーの最上位に出す。意図して置いたものなので、Inboxには出さない。
- 「種別を付ける」は種別の変更として扱い、IDと本文を保つ。中のObjectの所属は自動では変えない。

住所を種別のDBにする案とも矛盾しない。種別なしページは`page`のDBに入る。

### Inbox

ユーザーは、具象に紐づいているものは所属が確定しているのでInboxに出さなくてよいとした。ただしこれは、具象がContextになれた時点での判断である。具象がContextを持たない形に変えた後は、具象のページで状態なしに書いたMemoはContextが空になり、Inboxに入る。ユーザーも、後から紐づけられる点を利点として挙げている。

Claudeは、日記や雑記のように、どの活動にも属さないMemoがInboxに残り続ける点を挙げた。「活動なしで確定」を選べるようにして、未定のものと区別する必要がある。

### 活動をまたいだ紐づけ

ユーザーは、Memoにタグを付けるなど、活動を横断した紐づけがあるとよいと考えている。ただし、AIやTimelineの時間方向の隣接で補う形になるかとも述べた。

Claudeは、タグは具象で代わりになると答えた。#タグのような列を持たない種別を作り、Memoの参照の行に入れればよい。具象のページは参照しているものを活動ごとに分けて並べるので、それがそのまま活動を横断した一覧になる。時間方向の隣接はDailyとTimelineで、つけ忘れはAIの候補で補う。

活動に紐づくメモの集約という当初の目的は、Viewとテンプレートの機能を良くすれば実現できるのではないか、とユーザーは考えている。

## 次に判断すること

| 論点                     | まだ決めていないこと                                                                                     |
| ------------------------ | -------------------------------------------------------------------------------------------------------- |
| 種別なしページ           | 組み込みの種別`page`として持つ案を採るか。Memoとの違いを、見た目と使い方で説明できるか                   |
| 種別の付け外し           | 種別を付け外しするときのプロパティの扱い                                                                 |
| 既存データの移行         | 具象をContextにしていたObjectの移し方を、アプリを置き換える前の移行にどう入れるか                        |
| 活動なしの確定           | Inboxで「活動なしで確定」を選んだことを、どう持つか                                                      |
| 削除候補の置き場所       | 置き場所をなくしたObjectを、Inboxの欄に出すか、Viewに出すか                                              |
| 書いた場所の保存         | 書いた場所と「置き場所をなくした」印の保存方法。既存のObjectの書いた場所をどう決めるか                   |
| 書いた場所のページの削除 | ページをゴミ箱へ送るとき、そこを書いた場所とするObjectも一緒に送るか、置き場所をなくしたものとして残すか |
| 独立DB                   | 新しい概念として増やさず、種別とViewで表す案を採るか。一覧専用の列をどこへ保存するか                     |
| 活動ページ               | 集約の欄を縦に並べるか、タブに分けるか                                                                   |
| 用途テンプレート         | Projectの用途テンプレートに何を持たせ、共通の既定と就活・研究などの設定をどこまで用意するか              |
| 個別の例外               | 活動の木と選んだ具象だけで足りない場合に、Object単位の追加・除外が要るか                                 |
| 探索の深さ               | 活動の階層をたどる深さを、Viewで制限できるようにするか                                                   |
| AIの提案                 | 提案の保存先、承認の操作                                                                                 |
| 設定UI                   | 取得する具象の選択と、結果からの調整を、どの画面で行うか                                                 |

比較に使う例として、就活でCompanyを集める場合、研究でPaperを集める場合、共有Personを介するMemoの混在、種別なしページの下にTaskがある場合が挙がっている。これらを使って、設定する量と結果の分かりやすさを確認する必要がある。
